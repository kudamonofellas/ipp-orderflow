## Architecture Decisions

- **Design tokens live in `src/styles/tokens.css`** — single CSS file with all custom properties, sourced from `context/ui-context.md`. Dark theme via `[data-theme="dark"]` selector on `:root`. No Tailwind, no CSS-in-JS.
- **`context/ui-registry.md`** — the imprint skill's consistency registry. Baseline established 2026-07-07 before any component was built; moved from the workspace root into `context/` the same day so all context sources live in one folder. Derived from the dashboard design spec.
- **Dashboard is UI-first with mock data** — built the full Admin Dashboard shell against `Dashboard.png` using in-memory mock view-models (`src/data/mockDashboard.ts`), deferring Directus wiring to a schema-first unit per `ai-workflow-rules.md`. No localStorage/IndexedDB — mock data is transient and not a source of truth.
- **Open decision resolved for now: Dashboard defaults to the Admin view.** The role-scoped dashboard question remains open for other roles.
- **`context/ui-tokens.md`** — AI-facing quick reference, not the source of truth. `ui-context.md` wins on conflicts.
- **`localStorage` is allowed for local-only UI state that isn't business data** (e.g. the sidebar collapsed flag, the notifications "last read" cursor — see `useNotificationReadState`). Architecture.md invariant #2 bans `localStorage`/`IndexedDB` as the *source of truth for business data* (Directus/Postgres wins on conflict); it doesn't ban client-side caches of viewer-specific UI state that has no server-side equivalent to conflict with. If a feature needs real per-user server-tracked state (e.g. actual per-message read receipts shared across devices), that requires a Directus schema change and is a separate schema-first unit — don't reach for `localStorage` to fake that.
- **Returns are modeled as parallel buckets, not a linear sub-pipeline** (`returnBucketsForOrder()` in `pipeline.ts`). `order.stage` stays `'returned'` for the whole workflow; `awaiting_return`/`admin_action`/`awaiting_signed_doc`/`replacement_transit` are computed from `return_received`/`return_settle`/`return_doc`/`return_inbound`/`is_replacement` and can be simultaneously true — mirrors how Finance already runs alongside Cold Storage rather than blocking it. Any future code that touches return state should call `returnBucketsForOrder()` rather than comparing `stage` against a return-bucket key directly, since that comparison is never true.
